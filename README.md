# Resolve

Automated resolution infrastructure for long-tail prediction markets: register a market condition and its sources, and get back a strict, contract-validated verdict with evidence hashes and provenance.

```
{ market_id, resolution_status: RESOLVED|UNRESOLVED|ERROR, winning_outcome: OPTION_A|OPTION_B|NONE,
  confidence_score: 0.00-0.99, error_code: null|INSUFFICIENT_DATA|SOURCE_MISMATCH|UNSAFE_INPUT|UPSTREAM_UNAVAILABLE, ... }
```

How a verdict is produced: deterministic pre-checks (hidden-Unicode and injection markers, source allow-list, anchor localization, time window, integrity, language) → structured resolvers for machine-readable sources (GitHub API, Base and Solana logs, numeric thresholds) with a coverage proof before any negative verdict → otherwise one call to TypeSafe's Jev model with a fixed battery of typed questions → threshold post-checks → a verdict the database itself refuses to store if it violates the contract invariants.

Stack: TypeScript on Cloudflare Workers, Supabase Postgres (pg_cron + pg_net scheduling), Jev (`jev-1.13.0`, pinned).

## Evals

`evals/cases/*.jsonl` is a frozen failure-injection suite (classes A–I: clean structured, clean unstructured, insufficient/corrupt, source mismatch, ambiguous, malicious, router refusals, upstream faults, absence without coverage). `pnpm eval --mode replay` grades it deterministically. `evals/ingest-cases/cases.jsonl` freezes ingestion cases (`pnpm eval:ingest`): a non-200 answer or a redirect outside the registered source is a coverage gap and never evidence, and change detection hashes a projection of deciding fields, so repo counters and HTML churn never re-resolve a market. `evals/registration-cases/cases.jsonl` freezes registration cases (`pnpm eval:registration`): a watch is created only for a well-formed source of its kind that names the resolver's own subject, on a public https host, with a Solana account that exists and is not a program; a robots.txt rule that disallows the page makes the market unsupported_source, and a robots.txt that could not be read (5xx, 429, no answer) refuses the registration as unverified (nothing stored, retry) rather than recording a permanent verdict. `pnpm eval:mutate` switches off one rail at a time and requires the matching suite to go red for a grader reason while a control with every rail on stays green. `evals/whop.ts` holds the card webhook's signature cases (a genuine Whop delivery is accepted; a wrong, stale, tampered or differently keyed signature is refused), which the harness turns red by switching the signature rail off.

Every published accuracy or latency number is rendered from database rows (`eval_runs`, `bench_runs`, `v_track_record`), never typed by hand. No number is published until it exists.

## Track record

Every shadow verdict is recorded first and then posted to the public Telegram channel as `sha256(preimage)`, where the preimage is `platform:external_id|status|outcome|confidence|caveats|canonical_sha256|thresholds_version|nonce`. When the platform resolves, the reveal is a reply that prints the preimage and the nonce, so the commitment can be recomputed from the post alone. `GET /v1/track-record/verify?hash=<sha256>` answers for any commitment: before the reveal only that it exists and when it was posted (never the nonce), after it everything needed to recompute it. `/v1/track-record` counts each market once, by its latest commit, excludes test markets, counts the legs of one multi-outcome event (a ladder) as one event, and shows percentages (with 95 % Wilson intervals, per market and per event) only after 100 reconciled events per platform. A commit is deduplicated against the market's latest commit only, so a verdict that changes back is committed again and the final commit is always the current verdict. The legs of one event are posted as one message, and the channel never carries more than 15 commit or reveal messages a minute. A market is settled in one database transaction, only after its watch has made the post-deadline observation the absence rule needs; a commit can never land on a settled market. `median_lead_seconds` uses the platform's own resolution time only; lead times against a polled official time are reported separately as an upper bound.

## Early reveals and pricing

A tenant can follow a public shadow market (`POST /v1/markets/{id}/follow`) and receive each committed verdict privately the moment its commitment is recorded: `GET /v1/shadow/{market_id}` and the `shadow.committed` webhook, then `shadow.revealed` when the platform resolves. Early reveals are labeled as excluded from the public record and never carry the nonce or the preimage before the public reveal. Both events carry a `venue` object in the platform's own identifiers (a Limitless slug, condition id and proposed `winningOutcomeIndex`; a Polymarket condition id, slug, event id and proposed outcome label), and `GET /v1/shadow/export` returns every followed market as CSV or JSON. Credit packs can be paid by card through Whop, the merchant of record (`POST /v1/billing/checkout`, or the form on `/pricing`, once `WHOP_CHECKOUT_ENABLED` is `"1"`): Whop receives the tenant id, never the key, and its signed `payment.succeeded` webhook (`POST /webhooks/whop`, Standard Webhooks signature checked on the raw body) grants the pack's credits once per payment, while a refund or chargeback takes them back once, never below a zero balance (`src/billing/whop.ts`, `src/billing/whop-events.ts`). Plans and credit prices: [docs/pricing.md](docs/pricing.md); the venue offers: [docs/pilot-pack.md](docs/pilot-pack.md). What the fetcher requests and how a site opts out: `GET /bot`.

The first print of each official release the rail records is itself served as data: `GET /v1/prints` lists every series with its latest recorded period and its next scheduled release (free), and `GET /v1/prints/{series}/{period}` answers the stored first print (value as published, the text it was read from, when it was first observed, the source URL, the SHA-256 of the upstream body and the second source's status) for 1 credit, charged once per request by `charge_read()` (migration 022): a replay of the same `Idempotency-Key` is free, a release not recorded yet answers `status: scheduled` for 0 credits (`src/api/prints.ts`). Retention (migration 022): `purge_retention()` runs daily from pg_cron and keeps `loop_runs` and the evidence excerpts of markets that are no longer open for 30 days; the record's tables are never purged, and the 10-minute dispatch check reads `storage_status()` and alerts once the database passes 300 MB and again past 400 MB, and when the purge failed, has not run for 26 hours or lost its cron job.

## Deploying

`pnpm run deploy` (plain `pnpm deploy` is pnpm's own workspace command) runs `scripts/deploy.sh`. It refuses a working tree with uncommitted changes and a commit that is not on `origin/main` yet (push first). Then it runs every gate: typecheck, the tests, the frozen-suite check, eval replay (a missing Jev fixture is red), the ingestion, official_release and registration-policy suites (each frozen, then run), the strict mutation harness, the OpenAPI check, a read-only check that every migration is applied to the production database, and a Worker bundle build. It deploys only when every gate is green, and then requires `/health` to report the deployed commit as `git_sha` (a Cloudflare error page for the Worker fails it; a network that cannot reach `workers.dev` only warns). `pnpm run deploy:dry` runs the same gates without deploying. CI runs the same code gates on every push and pull request; it cannot run the migrations gate (Actions holds no database credentials).
